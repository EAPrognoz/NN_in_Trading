# Стандарт коду NN_in_Trading

Застосовується до вихідного коду MQL5 і OpenCL у проєкті. Джерело реалізації
спільних MQL5-макросів — `Experts/NeuroNet_DNG/NeuroNet_Definitions.mqh`.
У новому й зміненому коді використовуйте ці макроси в кожному застосовному
місці. Для наявного коду зберігайте публічні імена, входи, формати даних,
ідентифікатори шарів та порядок серіалізації.

## Загальні правила

- Для `.mq5` і `.mqh` використовуйте UTF‑8 без BOM, CRLF і кінцевий
  перенос рядка. Відступ — три пробіли. Табуляцію і хвостові пробіли видаляйте.
- У шапці зазначайте точне ім’я файла, назву безпосередньої директорії,
  наявні відомості про авторські права та перевірене посилання на публікацію
  фреймворка. Рамка має 70 символів. Текст шапки вирівнюйте праворуч, з одним
  пробілом перед кінцевою рискою. Для вбудованого `AlphaGen_Contract.mqh`
  враховуйте, що будь-який текст також входить до ресурсу OpenCL.
- `#property strict` у MQL5 вилучайте. Інші `#property` вирівнюйте в колонках.
  Під час форматування зберігайте значення директив. У нових заголовках
  застосовуйте захист від повторного включення. Для фасаду та умовних
  включень перевіряйте цикл залежностей перед зміною чинного захисту.
- Продовження списку параметрів вирівнюйте після відкривальної дужки.
  Після коми й навколо `=`, `<`, `>`, `&&`, `||`, `+`, `-`
  використовуйте компактний стиль, зберігаючи межі токенів.
- Пишіть `if(...)`, `for(...)`, `while(...)` і `switch(...)`.
  Фігурні дужки блоку розміщуйте на окремих рядках із відступом два пробіли
  від керівного рядка. Тіло має відступ три пробіли. Позначки `case`
  врівень з іншими операторами блоку `switch`, їхні тіла ще на три пробіли.
- Перед повними визначеннями функцій, класів і структур використовуйте
  рамку з одним коротким рядком `Ім’я - призначення`. Блоки вхідних і
  глобальних змінних позначайте рамками. Усередині пов’язаних груп
  вирівнюйте імена й кінцеві коментарі в колонках. Оголошуйте по одній
  змінній на рядок, зберігаючи область видимості та послідовність ініціалізації.
- Усі коментарі у вихідному коді пишіть англійською, включно з рамками,
  блоками `Input parameters` і `Global variables`, Doxygen та підписами
  `input`, що задані кінцевими коментарями. Зберігайте ідентифікатори,
  посилання, теги документації, рамки та зміст. Для перекладу редагуйте
  лише лексичні коментарі. Рядкові літерали, зокрема назви `input group`
  і повідомлення журналу, потребують окремого рішення.
- Відділяйте змістові блоки порожніми рядками. Коментар `//---` ставте
  над кодом, який він пояснює. Верхньорівневий коментар у тілі функції
  починайте з першої колонки, вкладені коментарі вирівнюйте за блоком.
  Підписи `input` та Doxygen зберігайте.
- Для звичайних результатів використовуйте `return(expr);`, а для
  повернення без результату — `return;`. Для виразів на кшталт
  `return vector<float>::Zeros(...);` зберігайте форму без зовнішньої пари
  дужок, яку приймає MetaEditor.
- У файлах `.cl` дотримуйтеся відступів і узгоджених імен аргументів.
  Зберігайте OpenCL-типи, qualifiers, індексацію й порядок аргументів.
  MQL5-макроси належать стороні хоста та не використовуються в тілах ядер.

## Оголошення класів

- Спочатку оголошуйте всі поля, потім усі методи. У кожній із двох
  груп дотримуйтеся порядку `public`, `protected`, `private`. Пропускайте
  порожні секції та зберігайте рівень доступу кожного наявного члена.
- Залишайте визначення методу в класі, якщо тіло займає не більше трьох
  непорожніх рядків. Рахуйте рядки з коментарями, але не рахуйте
  сигнатуру, список ініціалізації конструктора та зовнішні фігурні дужки.
  Для довшого методу залиште в класі оголошення й винесіть визначення за
  межі класу з кваліфікованим іменем `Ім’яКласу::Метод`. Зберігайте
  сигнатуру, специфікатори оголошення й умови препроцесора.
- Перевіряйте порядок ініціалізації та розкладку полів, якщо перенесення
  між секціями впливає на них.

## Обов’язкові спільні макроси

| Макрос | Застосування |
| --- | --- |
| `CreateKernel(id,name)` | Реєстрація ядра через `opencl.KernelCreate` з виходом `false` у разі помилки. |
| `setBuffer(kernel,id,buffer)` | Передавання буфера через `OpenCL.SetArgumentBuffer`. |
| `setArgument(kernel,id,value)` | Передавання скалярного аргументу через `OpenCL.SetArgument`. |
| `kernelExecute(kernel,offset,global)`, `kernelExecuteLoc(kernel,offset,global,local)` | Запуск із розмірністю `global.Size()`. Другий макрос передає локальний розмір роботи. |
| `ReturnFalse`, `ReturnFalseEx(context)` | Обов’язкові для аварійного виходу з `false`. `ReturnFalse` пише в журнал функцію й номер рядка, `ReturnFalseEx(context)` додає причину чи контекст. Пряме `return(false);` використовуйте для штатного результату предиката. |
| `DeleteObj(obj)`, `DeleteObjAndFalse(obj)` | Видалення динамічного об’єкта після перевірки. Другий макрос також завершує функцію з `false`. |
| `dActivation(obj)`, `Deactivation(obj)` | Застосування активації й похідної з перевіркою `Activation()!=None`. |
| `dWeightsUpdate(obj,source,tau)` | Оновлення ваг із тим самим шаром джерела, приведенням до об’єкта і коефіцієнтом `tau`. |
| `dFileWriteUInt(handle,value)`, `dFileWriteFloat(handle,value)` | Запис 32-бітних значень із чинною перевіркою кількості байтів. |
| `dFileReadUInt(handle,value)`, `dFileReadUFloat(handle,value)` | Читання в уже оголошену змінну з перевіркою кінця файла. |

Макроси розгортаються в оператори. Файлове читання містить два оператори.
Для гілок `if/else` і тіл циклів із макросами використовуйте фігурні дужки.
Ставте виклик окремим рядком і звіряйте, чи розгортання вже містить
крапку з комою. Перед міграцією перевіряйте регістр і доступність `opencl`
або `OpenCL`, тип результату, порядок обчислення аргументів, робочі
розміри й чинні дії на помилці. Для макросів запуску використовуйте імена
підготовлених масивів без побічних ефектів у виразах аргументів.

Якщо прямий виклик повертає статус для відкладеної перевірки, містить
fallback, повтор, rollback, інший тип результату, використовує інший
OpenCL-контекст або виконує особливе очищення, збережіть цей контракт.
Використайте макрос у сумісній частині операції. Коли чинний макрос
неможливо застосувати без зміни поведінки, коротко поясніть причину поряд
із нестандартним шляхом. Новий спільний макрос має спиратися на кілька
реальних споживачів і перевірений спільний контракт.

## Перевірка змін

1. Звірте всі торкнуті місця з визначеннями макросів, включно з
   умовними гілками та серіалізацією.
2. Виконайте `git diff --check`. Для чистого форматування окремо перевірте
   незмінність токенів і збирання MetaEditor. Для міграції на макроси
   перевірте еквівалентність розгортання та очікувані діагностичні зміни.
3. Скомпілюйте змінені точки входу і прямих та транзитивних споживачів
   змінених заголовків. Ціль — 0 помилок і 0 попереджень. Зміни в OpenCL,
   буферах, синхронізації або серіалізації додатково перевіряйте виконанням
   на відповідному пристрої й контрольним збереженням та завантаженням.
