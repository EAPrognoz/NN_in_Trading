# Ведомость GPU AlphaQCM r8

Ведомость относится к штатному профилю IQN-QCM-v1. Объёмы ниже относятся к полезным данным буферов. Фактическая занятая память включает выравнивание, память драйвера и служебные буферы базовых слоёв. Память OpenCL-программы и ресурсы других приложений также учитывает устройство при выделении.

## Обозначения

| Параметры | Значения |
| --- | --- |
| Логический пакет `B`, replay `D`, кандидаты `C` | 128, 100 000, 8 |
| Длина токенов `L`, словарь `A`, embedding `E` | 20, 33, 32 |
| Search hidden `H`, частоты `M`, точки QCM `K`, квантили `N/N′` | 64, 64, 64, 64/64 |
| Рыночное окно `W`, контекст `J`, вместимость банка `P` | 512, 256, 101, включая рабочий слот |
| Торговый hidden `T`, rollout `U`, Account13 и Action6 | 32, 128, 13 и 6 |

`p` — физическое число строк learner, `g` — число одновременно генерируемых кандидатов, `h` — размер порции оценки формул, `S=W+J−1=767`. FP32 и int32 занимают 4 байта, uint64 — 8 байт. Формулы в таблицах указаны в элементах указанного типа.

В стоимости VERIFY их считать отдельно. |

Источники раскладки — `CAlphaQCMReplay::Configure`, `CNeuronAlphaQCMEncoderOCL::Workspace`, `CAlphaQCMObjective::Reserve`, `CAlphaQCMGenerator::Configure`, `CAlphaGenPool::Configure` и `CAlphaGenPool::QCMValidateWorkspace`, `CNeuronAlphaQCMOCL::TradeWorkspace`. Базовые буферы слоёв относятся к их владельцам и добавляются к указанным максимумам. 58 буферов staging и вычислений четырёх энкодеров и 11 буферов objective могут жить одновременно с постоянными структурами.

Базовые выделения также можно учесть по формулам. Для стандартного ADAM-слоя с `I` входами и `O` выходами базовые output, previous output и gradient требуют три FP32 буфера по `I`. Если `O>0`, добавляются ещё три массива по `(I+1)O` для веса и моментов. Для донорского dense поверх базы выделяются два численных буфера по `I`, один scalar и, при `O>0`, градиент размера `(I+1)O`. Итого 10 буферов при наличии матрицы или 6 для head без весов. Донорский LSTM с входом `I`, hidden `F` и ёмкостью `D_t` имеет 16 буферов: 3 базовых по `F`, 4 рабочих `2F,F,4F,4F`, 4 матричных по `4F(I+F+1)` и 5 собственных `6D_tF,2F,D_tF,D_tF,4D_tF`. Для двух донорских LSTM каждого поискового энкодера `D_t=L`, для торгового `D_t=W`. Эти матричные буферы входят в строку параметров и при суммировании второй раз не учитываются.

В TRAIN одновременно могут жить 142 явно перечисленных буфера replay, learner/staging, generator, pool, evaluator и надстройки композита. Поверх них прибавляются 268 буферов донорских объектов четырёх поисковых сетей (по два LSTM и три или четыре dense) и 58 буферов торговой policy, включая её LSTM, три dense-матрицы, head без весов и 6 собственных буферов. Из 268 поисковых буферов 88 — уже описанные матричные данные. К сумме прибавляются базовые входные и выходные слои пяти `CNet`, базовый evaluator и сервисные буферы приложения. Для расчёта их ёмкости применяются формулы базы выше с геометрией фактических слоёв. `BuildNetwork` задаёт размеры `L,A`, `InitializeModel` задаёт `5W+13,6`, evaluator имеет `W` элементов, service — `22+5W` элементов.

## Нижняя граница и разделение по режимам

| Составляющая | Минимальное физическое разбиение | Полный физический пакет |
| --- | ---: | ---: |
| Online Q и IQN, target Q и IQN, objective, вместе | 416 940 байт при `p=1` | 53 081 808 байт при `p=128` |
| Replay | 24 946 644 байта | 24 946 644 байта |
| Generator | 102 088 байт при `g=1` | 419 328 байт при `g=8` |
| Pool, исходная граница `QCMValidateWorkspace` | 1 054 104 байта, крупнейший буфер 619 736 байт | Увеличивается с порцией `h`. Global-history вариант дополнительно требует 14 336 байт при `h=1`. |

Только перечисленные четыре семьи требуют не менее 26 519 776 байт в TRAIN. К этому добавляются постоянно живущие параметры/моменты, торговые данные, донорские буферы и служебные буферы фреймворка. Проверяемый нижний предел одного allocation — 10 400 000 байт для state replay. Этот предел и сумма нижних оценок не гарантируют, что все allocations поместятся на конкретном устройстве. Для trading LSTM runtime проверяет минимум четыре параллельных lane и фактическую local memory после binding. На Intel Iris Xe журнал предыдущей приёмки указывает 3 072 байта для forward и 2 048 для backward. Для portable replay/generation требуется минимум два lane. Драйвер 32.0.101.7092 сообщил local memory 65 536 байт, global memory 7 450 615 808 байт и max allocation 3 725 307 904 байта.

Runtime проверяет тип GPU, OpenCL C 1.2, FP32, размеры WG, global/local memory и max allocation. Generator и pool уменьшают физическую порцию по результату allocation, learner уменьшает `p` до делителя `B` и повторно резервирует четыре сети и objective. При невозможности минимального параллельного запуска штатный результат — `RESOURCE_UNSUPPORTED`. Логические размеры профиля остаются фиксированными.

**INFER** содержит торговую сеть и данные сохранённого пула. В этом режиме отсутствуют четыре поисковые сети, replay, generator, objective и торговый rollout. **VERIFY** выполняется в общем OpenCL-контексте поверх работающего TRAIN. Для пика сохранения требуется добавить живые донорские объекты второго `CNet` и его базовые буферы к штатному TRAIN. Replay проверяется на CPU порциями по 256 строк, по `256·[4(L+6)+8·6+2·4]=40 960` байт для полезных данных порции. Второй полный replay и второй learner на GPU не выделяются. При обычном TRAIN Load временные host-массивы restore могут занимать до `D·[4(L+6)+8·6+2·4]=16 000 000` байт и освобождаются после Build и переноса на устройство.
